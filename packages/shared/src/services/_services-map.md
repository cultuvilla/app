# Services map

This is the catalogue of every backend-touching function in the app. **All Firebase access flows through this directory.** Components, pages, and hooks must call services here — no direct `firebase/*` imports outside this folder (the auth listener in `AuthContext.tsx` is the one documented exception). See [AGENTS.md](../../../../AGENTS.md) for the rule.

When you add a service, add it to this file in the same change. When you add a function to an existing service, update the row below.

> Collection paths reflect today's architecture: **first-class top-level collections** (`events/`, `organizations/`, `news/`, …) scoped by a `municipalityId` field, plus a small number of genuinely nested collections (`users/{uid}/notifications/`, `events/{eventId}/registrations/`, `organizations/{orgId}/members/`, `municipalities/{id}/members/`). See AGENTS.md §3 for the rationale.

## Placement decisions (non-obvious)

The catalog above tells you *what* each service owns. This section tells you *why* a piece of logic lives where it does — the calls that are hard to recover by grep, and the cross-service interactions that aren't obvious from a single file.

Add to this section as you touch a domain. Incremental beats one big sweep.

### Village / municipality membership

- **`organizerRequestService` splits client reads from callable-only writes.** Reads (`getMyOrganizerRequests`, `getPendingOrganizerRequests`, …) use direct Firestore queries. Mutations (`requestOrganizeVillage`, `respondToOrganizerRequest`) are `httpsCallable` wrappers because the response path must also write to membership/admin docs the requester can't reach. Joining a village, by contrast, is a **direct client write** (`joinVillage` — an atomic member+residence-link batch, then `setActiveMunicipality`) gated by Firestore rules — no callable, no approval.
- **`villageMemberService` owns `municipalities/{mid}/members/{userId}` writes, but `membershipProfileService` writes `profileCompletedAt` on those same docs.** The answers themselves live in the private `censoAnswers/` doc, never on the world-readable member doc (whose `profileAnswers` stays `{}` for installed binaries).
- **`organizationService.requestOrganization` writes to `organizations/`, NOT to `organizerRequests/`.** `organizerRequests/` is for *requesting to become organizer of an inactive municipality* (a different flow). Don't confuse the two.
- **`requestOrganization` routes by type: `peña` / `asociación` are direct client writes; `ayuntamiento` goes through the `requestAyuntamiento` callable** ([functions/src/organizations/requestAyuntamiento.ts](../../../../functions/src/organizations/requestAyuntamiento.ts)). An ayuntamiento is a singleton per village and `firestore.rules` denies client-side ayuntamiento creates — the callable enforces the cap in a transaction (rejects a second pending/approved one).

### Events / registrations / feed

- **`registrationService.registerToEvent` is a thin callable wrapper around [functions/src/events/registerToEvent.ts](../../../../functions/src/events/registerToEvent.ts).** Capacity-vs-waitlist decision and `confirmedCount` increment happen inside a Firestore transaction in the function — never client-side. Direct `registrations/` writes from the client would race the count.
- **`feedService` queries top-level `events/` directly**, not a collection group. (The earlier collection-group-on-`events` shape is gone since the Open Feed migration — see [docs/decisions/open-feed-architecture.md](../../../../docs/decisions/open-feed-architecture.md).) `feedService` is read-only — anything that mutates an event still goes through `eventService`.
- **Every list query over `events/` pins `visibility` or `visibilityOrgId`.** An
  event may be private to one organization (`visibility: 'organization'` +
  `visibilityOrgId`), and Firestore rules are not a filter: a `list` rule that
  turns on a field the query leaves unconstrained is evaluated against what the
  query *could* return, so an unpinned query either hands back the private rows
  or fails outright. Hence the split — `getUpcomingFeed` /
  `getEventsByMunicipality` ask for public events only, and
  `getPrivateUpcomingFeed` / `getPrivateEventsByMunicipality` fetch the private
  half **one org at a time** (never an `in` over several), so every row a page
  returns resolves the same membership document in the read rule. Callers get
  the viewer's org set from `orgMemberService.getUserOrgIds`.
- **`feedService` does in-memory haversine filtering after Firestore returns.** No geo index — caller is expected to pull a reasonable village set first, then filter by distance. If a "nearby events" surface ever needs server-side geo, that's a feature add, not a bug.
- **Cancellation/edit notifications come from [functions/src/events/notificationTriggers.ts](../../../../functions/src/events/notificationTriggers.ts), not from `eventService.updateEvent`.** Client-side notification fan-out would require writing to every registrant's `users/{uid}/notifications/` — outside the writer's security boundary.
- **A registration's PII never touches the roster doc.** `events/{eid}/registrations/{rid}` is readable by every member of the event's pueblo, so the phone, every custom `signupFields` answer and the attendee's birth date live in `events/{eid}/registrationPrivate/{rid}`, gated to event organizers in `firestore.rules` and writable only by the `registerToEvent` / `claimEventSeat` / `addWalkInRegistration` callables. Read it via `getRegistrationPrivate`; never add an answer, phone or birth-date field to `RegistrationData`. The birth date is a point-in-time copy of `persons.birthday` like the roster's photo and name — reading `persons` per row is not an option for an organizer anyway, since a private persona's doc is denied to everyone but its creator.

- **The roster is village-scoped, not public.** `events/{eid}/registrations/` is readable by members of the event's `municipalityId` when the event's `attendeesVisibility` is `members` (the default), by the organizer set / admins always, and by a registrant for their own row (a visitor from another pueblo signs up too). It is **not** world-readable — a roster names real people, including dependent personas whose `persons` doc is deliberately private. `isPersonPublic` on the registration is what lets the UI count such a persona without naming it; anything that writes a registration must set it honestly.

- **Waitlist promotion is owned by [functions/src/events/waitlistPromotion.ts](../../../../functions/src/events/waitlistPromotion.ts), triggered on registration delete.** Promotion happens server-side because the candidate registration belongs to a different user. On an event with `signupGroupSize > 1` it promotes a whole *group* or nobody — half a pareja is exactly what the setting exists to prevent.

- **`cancelRegistration` is a callable, not a delete.** `firestore.rules` denies client deletes on `registrations` outright ([functions/src/events/cancelRegistration.ts](../../../../functions/src/events/cancelRegistration.ts) is the only path). A group is atomic, so cancelling one seat must take the whole group or leave it whole at full size, and rules can neither read the sibling seats nor require the companion deletes. The three outcomes — `delete-solo`, `delete-group`, `release-seat` — are decided by `resolveCancellation`.

- **The roster's history lives in `events/{eid}/registrationEvents/`, because cancellation is a hard delete.** `cancelRegistration` removes the registration doc outright, so an append-only entry written in that same transaction is the only record that the attendee was ever there — and the only place "an organizer removed them" is distinguishable from "they left". Written exclusively by the registration callables and the `onEventUpdated` sign-ups sweep via the admin SDK ([functions/src/helpers/registrationAudit.ts](../../../../functions/src/helpers/registrationAudit.ts)); every client write is denied. Read by `getRegistrationEvents`, gated in `firestore.rules` to `isEventOrganizer(eventId)` — organizers, village admins, app admins — and deliberately NOT to the pueblo, however open `attendeesVisibility` is. A subcollection rather than a top-level `municipalityId`-scoped log (cf. `membershipEvents`) so that rule's `get()` on the event is paid once per query instead of once per row.

- **An open group seat is a held registration, not a pending one.** It occupies capacity from the moment the group is booked, which is why claiming it ([functions/src/events/claimEventSeat.ts](../../../../functions/src/events/claimEventSeat.ts)) is a reassignment rather than a sign-up: no third registration status, no expiry sweeper, no counter change. `userId` moves to the claimer; `groupOwnerId` keeps pointing at whoever booked the group.

### Census / occupation

- **`censoService.updateCensoSchema` is a callable wrapper around [functions/src/census/updateCenso.ts](../../../../functions/src/census/updateCenso.ts).** The function validates the schema transition (no forbidden field-type changes) and stamps `censoUpdatedAt` on the municipality doc. Client-side schema mutation would bypass the validation.
- **`occupations/` is now collected free-text (Task 11), not a moderated taxonomy** — `recordOccupation` upserts `occupations/{slug}` directly from the client; there is no proposal/review step. The `occupationProposals/` collection and its `onOccupationProposalApproved` trigger were removed (Tasks 11–12); `persons/{pid}.occupations` is now a single free-form string array.
- **Censo answers are private, completion is not.** `saveProfileAnswers` writes the answers to `censoAnswers/{municipalityId}_{uid}` and `profileCompletedAt` to the member doc in one batch. Never put answer content back on the member doc: it is world-readable.

### News

- **`newsService` owns the `news/` top-level collection**, scoped by `municipalityId`. Comments are no longer news-specific — they live in the generic `comments/` collection owned by `commentsService`, entity-scoped via `entityKind`/`entityId`. User-filed reports live in the generic `contentReports/` collection owned by `contentReportService`; there is no reactions/likes feature.
- **Comment counts on the post doc (`commentCount`) are denormalized by a trigger, not by the writer.** `syncEntityCommentCount` ([functions/src/interaction/syncEntityInteractionCounts.ts](../../../../functions/src/interaction/syncEntityInteractionCounts.ts)) watches the generic `comments/` collection and routes by `entityKind` to whichever entity doc owns the count — same trigger backs all six entity kinds, not just news. `readCount` is unrelated: it has no source collection and is incremented directly by the `recordEntityView` callable, fired fire-and-forget from each detail screen on mount.
- **Moderation lives in functions** ([functions/src/moderation/setContentVisibility.ts](../../../../functions/src/moderation/setContentVisibility.ts), [functions/src/news/deleteNewsPost.ts](../../../../functions/src/news/deleteNewsPost.ts)), not in `newsService`. Cross-user writes (deleting another user's post, hiding/unhiding content) require admin scope. `deleteNewsPost` cascades the post's `comments` with the admin SDK.
- **`getHomeFeed` and `getOtherVillagesFeed` are split queries**, not one feed with a filter. Home feed = the user's own subscribed villages; other-villages feed = everything else, paginated separately. Two indexes, two cursors — don't try to merge. **`getAllVillagesFeed`** is the cross-village superset (every approved post, ordered by `publishedAt`) backing the Explora feed; callers narrow by village client-side.

### Identity / users / persons

- **`userService` owns the `users/{uid}` doc only.** `setActiveMunicipality` flips a single field on that doc; the village-membership-side of "which villages does this user belong to" is `villageMemberService.getUserMemberships` (collection-group query over `members/`). Don't denormalize membership lists onto the user doc — the membership doc IS the answer.
- **`personService` writes `persons/{pid}` (top-level, `creatorUserId` field), not nested under users.** Personas are crosslinked to events via registrations; keeping them top-level lets a future "manage personas across multiple municipalities" surface work without a doc move.
- **`isAppAdmin` in `adminService` reads `admins/{uid}`, not a flag on the user doc.** Separate collection so a leaked user doc never tells an attacker who the superadmins are; and admin-status checks don't trigger user-doc reads from screens that don't otherwise need the user doc.

### Cross-cutting

- **`imageService` is the single writer for Storage uploads from the client.** Never call `firebase/storage` directly from a component — `imageService` enforces mime+size limits and produces the public URL shape that gets stored on Firestore docs. Downscaled `_card`/`_thumb` renditions are *derived*, not stored on any doc: `functions/src/images/generateImageVariants.ts` writes them beside the original and the client addresses them by rewriting the URL (`variantImageURL` in `@cultuvilla/shared/utils`), so adding a rendition never touches a schema. Image *deletes* from Storage that the server triggers (on event/news/person delete) happen in functions, not here.
- **Push is a projection of the notification log, never a parallel channel.** Every producer writes a `users/{uid}/notifications/` doc and nothing else; the single trigger [onNotificationCreated](../../../../functions/src/push/onNotificationCreated.ts) turns it into a device push (preference check → quiet hours → idempotent `pushQueue/{uid}__{nid}` enqueue → FCM for Android / APNs for iOS). A new producer gets push for free; don't send a push from a producer. The Android/iOS behaviour differences live only in [PushEnvelope.ts](../models/notification/PushEnvelope.ts). See [docs/plans/ongoing/device-notifications.md](../../../../docs/plans/ongoing/device-notifications.md).
- **"Something new in your village" is one broadcast for the whole entity family** ([entityPublishedTriggers.ts](../../../../functions/src/village/entityPublishedTriggers.ts), type `village_entity_published` + `entityKind`). Organizations broadcast on approval, from `onOrganizationUpdated`, not on create.
- **`notificationService` is client-write-only** for the *current user's* `users/{uid}/notifications/`. Notifications *to other users* must go through a Cloud Function — security rules forbid writing to a different user's subcollection. (Pattern: domain function writes the notification doc; the recipient's app picks it up via subscription.)
- **`observability` (in `services/observability/observabilityService.ts`) is a platform-free port, not a Firebase-backed service — it owns no collection.** Screens/hooks call `observability.trackEvent`/`captureError`/`logger.*`/`setUserContext`/`setConsent`/`startOperation` directly; only the app-level adapter wired via `configureObservability` (mobile: `apps/mobile/lib/observability/configure.ts`) touches `firebase/*` (Firebase Analytics) or `httpsCallable` (the `logClientError`/`getUserIdHash` Cloud Functions, `functions/src/observability/`). `filterContext` enforces the single PII allowlist (`ALLOWED_CONTEXT_KEYS`: `uid, municipalityId, villageId, role, appVersion, platform, route, operation_id`) before anything reaches an adapter — never pass a raw object past it. `trackEvent` is gated on `setConsent({ analytics })`; `captureError`/`logger.*` are not — crash/error diagnosis flows regardless of consent. Event names come only from `OBSERVABILITY_EVENTS` (`observabilityEvents.ts`), never an inline string. Client errors reach Cloud Logging/Error Reporting via the `logClientError` callable, which stamps the server-authenticated uid (never trusts a client-supplied uid) before hashing it (`OBSERVABILITY_USER_ID_SALT`, HMAC-SHA256) through the server-side `log.*` chokepoint in `functions/src/shared/observability.ts` — see the `observability-conventions` skill.
- **Live reads are `watch*` twins of `get*` reads, built on [watch.ts](watch.ts)** (`watchQuery`, `watchQueryWith`, `watchDoc`, `watchMerged`, `watchDocsByIds`, `watchCount`). Each twin shares its query builder or typed doc ref with the getter, so the query shape and its index have one source. Screens subscribe through `useWatch` (`apps/mobile/lib/hooks/useWatch.ts`); on the native SDK a listener answers from the device cache first, so the screen paints at once — offline too — and stays current without reloading on focus. The village home, the Inicio feeds and every entity detail screen (`watchEvent`, `watchPlace`, `watchBarrio`, `watchFestivalPoster`, `watchHistoryEntry`, `watchVocabularyTerm`, `watchNewsPost`, `watchOrganization`) read this way, as do the history and vocabulary lists, Mis inscripciones, the profile and the bell badge. **There is no `getCountFromServer` left:** a server count cannot answer offline, so a count is either a stored counter on a doc or `watchCount` over a small, already-bounded result (a user's unread notifications). See [docs/plans/ongoing/offline-first-village.md](../../../../docs/plans/ongoing/offline-first-village.md).
- **`municipalityService` owns nested collections (`barrios/`, `places/`) under the same parent.** These are read-heavy reference data; the nested layout keeps them adjacent to the municipality doc that owns them. `places/` holds notable sites discriminated by `kind` (`cemetery`, `church`, …); `kind === 'cemetery'` is the target of `Person.burialPlace`. If you find yourself doing a collection-group query over `barrios` or `places`, that's the signal to denormalize the field onto the consuming doc instead.

## How to add a service

1. Create `packages/shared/src/services/{name}Service.ts`.
2. Export from [index.ts](index.ts).
3. Add a row to this file: collection it owns, what it does, key entry points.
4. If it denormalizes onto another doc, add the trigger and a row in the table above.
5. If the placement is non-obvious — e.g. mutations go through a callable instead of direct writes, or the service splits ownership with another service on the same doc — add a bullet to "Placement decisions" with the *why*.
6. Consume from components/hooks via `@cultuvilla/shared/services/...`.
